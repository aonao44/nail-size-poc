## 🔴 確認事項（優先度順）

### 1. 【仕様矛盾】画像2（横）で長さを推定する際のスケール基準

プロンプト 5-2 では「画像1から算出したピクセル-mm比率を **同じ比率** で画像2に適用」とありますが、
**画像1（真上）と画像2（真横）ではカメラと被写体の距離・画角が異なるため、同じピクセル-mm比率は成立しません。**

→ 画像2にも500円玉を写してもらい、**各画像でそれぞれ比率算出する設計** に変更するのが妥当だと思います。
  その場合、ガイド枠（Step2 側）とプロンプトの両方を修正する必要があります。

**質問:** この方針（画像2にも500円玉を含めて、それぞれの画像で独立にスケール算出）で進めて問題ないですか？

---

### 2. 【精度リスク】Gemini Vision での mm レベル計測の妥当性

Gemini 2.x Flash は画像内の **ピクセル計測タスクが苦手** です
（定性的理解は得意ですが、ピクセル距離の正確な算出は弱い）。
±2〜3mm の誤差が出ると、サイズが 1〜2 個分ズレる可能性があります。

**質問:** 本 PoC のゴールは以下のどちらですか？

- **A. 動くデモを作る**（精度は二の次、UX とフロー検証が目的）
- **B. 精度を検証する**（実際に使えるレベルかを確認するのが目的）

→ B の場合は、最初に数サンプルで精度実測を行ってから本実装に進むほうが安全です。
  その場合、簡易スクリプトで先にプロンプト検証するフェーズを挟むことを提案します。

---

### 3. 【技術】画像ペイロード肥大化への対応

スマホの高解像度写真を base64 で2枚 JSON 送信すると **数 MB** に達し、以下の上限に抵触します。

- Next.js API Route の body 上限（デフォルト 4MB）
- sessionStorage の上限（約 5MB）

**質問:** クライアント側で **長辺 1024px にリサイズ + JPEG 品質 0.85** に圧縮してから送信する前提で実装してよいですか？
（画質は解析に十分、ペイロードは 200〜400KB/枚に収まる想定）

- **Gemini モデル:** `gemini-2.0-flash` は旧世代。`gemini-2.5-flash` のほうが精度・速度とも有利。

**質問:**
- Next.js は **14 / 15** どちらで進めますか？
